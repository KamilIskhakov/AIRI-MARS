# Пайплайн оценки семантики подстановок

## 1. Целевая задача

Для исходного контекста `A = C[e]` и текста после замены `B = C[c]` модель должна оценить, сохранилось ли утверждение. Кандидат считается ценным отрицательным примером, если он грамматически и тематически правдоподобен, но меняет факт или референт. Случайное далёкое слово почти бесполезно: его легко отличить без понимания смысла.

Нельзя смешивать три разных сигнала:

- `MLM fit`: естественно ли `c` выглядит в позиции;
- `preserved`: сохранился ли смысл после подстановки;
- `A => B` и `B => A`: какие направленные следствия сохранились.

Высокий MLM-score не является положительной меткой. Для hard negative как раз нужен высокий `MLM fit` при низком `preserved`.

## 2. Что уже пригодно для обучения

Канонический корпус собирается в `data/semantic_corpus_v1_20260819`.

| Часть | Строк | Назначение | Статус |
|---|---:|---|---|
| proper names | 24 836 | псевдонимы и сложные подмены | основной обучающий корпус |
| common nouns, audited | 109 | преимущественно сложные отрицательные | дополнительный challenge-набор |
| старый broad judge | 6 752 | почти одноклассовая старая разметка | автоматически не смешивать |

После удаления конфликтов и одинаковых входов в фиксированном корпусе 24 935 строк: 12 989 `changed` и 11 946 `preserved`. Разбиение train/validation/test сделано по связанным компонентам `entity + document`, поэтому одна исходная сущность или один документ не попадают в разные части.

Common-ветка пока несбалансирована: 106 отрицательных и только 3 положительных примера. Числовой ветки в обучающем корпусе ещё нет. Следовательно, текущая модель пригодна прежде всего для имён собственных; общую метрику нельзя выдавать за качество на всех типах сущностей.

## 3. Контроль качества разметки

Перед каждым обучением выполняются автоматические проверки:

1. Нормализованное равенство `entity == candidate` запрещено.
2. Полные модельные входы `left == right` запрещены.
3. В обоих контекстах должна находиться соответствующая сущность.
4. Конфликтующие дубликаты с разными метками исключаются.
5. Train/validation/test не пересекаются по исходным сущностям, документам и точным модельным входам.
6. Случайная стратифицированная выборка пересуживается вслепую: судья не видит исходную метку.
7. Считаются agreement, Cohen's kappa и ошибки отдельно по ветке, типу сущности и исходному классу.

Порог допуска в основной train:

- два независимых судьи согласны;
- ответ не `uncertain`;
- уверенность не ниже принятого порога;
- все автоматические инварианты выполнены.

Разногласия не выбрасываются: они образуют challenge/review-набор. Это наиболее полезные примеры для ручного аудита и будущего active learning.

## 4. Разные ветки генерации

### Имена собственные

Для `ORG`, `PERSON`, `GPE`, `LOC`, `FAC`, `EVENT`, `LAW`, `PRODUCT`, `WORK_OF_ART`, `NORP` используется полный контекст. LLM генерирует:

- положительные псевдонимы, аббревиатуры и подтверждённые варианты того же референта;
- сложные отрицательные сущности того же типа и домена, которые правдоподобны в предложении, но обозначают другой объект.

ModernBERT здесь не должен генерировать многотокенные названия. Он может оценивать MLM-fit или переранжировать пул реальных сущностей из SQLite.

### Нарицательные сущности

1. Агент подтверждает тип `common_entity`/`domain_term` на инвентаре.
2. В SQLite выбираются реальные упоминания и восстанавливается контекст.
3. ModernBERT MLM маскирует целевую позицию и предлагает top-K однотокенных существительных.
4. Отдельный Mistral-генератор предлагает осторожные контекстные синонимы для положительного класса и близкие сложные отрицательные; это компенсирует то, что MLM top-K в основном даёт отрицательные примеры.
5. Удаляются identity, регистр, простые singular/plural и лексический мусор.
6. Для каждого кандидата считается MLM-fit исходной и заменённой сущности.
7. Mistral и второй независимый провайдер судят полные тексты, не видя гипотезу генератора.
8. В train попадает только консенсус; остальные строки идут в review.

Для экономного bootstrap допускается отдельная локальная ветка
`mvp/run_common_weak_generation.sh`. Она не вызывает Mistral: encoder retrieval
формирует близкие кандидаты, WordNet добавляет прямые синонимы, а правила удаляют
морфологические варианты. Такие строки получают именно `weak_label`, а не
утверждение о гарантированной семантической эквивалентности. После калибровки на
небольшом стратифицированном сэмпле их можно использовать для предварительного
обучения или как challenge-набор; финальные метрики считаются на независимой
агентной/ручной выборке.

Косинус эмбеддингов и MLM-fit используются только для поиска близких кандидатов. Значение 0.8/0.9/0.97 само по себе не определяет правильность замены.

### Числа, даты и величины

Для `DATE`, `TIME`, `CARDINAL`, `ORDINAL`, `MONEY`, `PERCENT`, `QUANTITY` генератор использует окно из одного-двух слов слева и справа. Гипотеза состоит в том, что число чаще всего связано с ближайшей сущностью или единицей измерения непосредственно перед ним либо после него.

Генерируются два класса кандидатов:

- эквивалентная запись: `$600 million` -> `600 million dollars`, `1.7 percent` -> `1.7%`;
- близкое фактологическое изменение: `Feb. 23` -> `Feb. 24`, `$600 million` -> `$660 million`.

Короткое окно используется для генерации, но окончательный суд выполняется по восстановленному контексту. Это отсеивает ложную типизацию, например номер модели самолёта как обычное количество.

## 5. ModernBERT как две независимые оси

Локальный checkpoint действительно имеет `ModernBertForMaskedLM`, поэтому он используется без отдельного генеративного декодера.

Для многотокенного кандидата MLM-fit вычисляется как средний log-prob его токенов при одновременном маскировании span. Это приближение псевдоправдоподобия, а не точная авторегрессивная вероятность.

После обучения cross-encoder для кандидата доступны:

```text
fit(c)       = MLM(C[MASK], c)
preserve(c)  = CE(C[e], C[c])
```

Выбор hard negative выполняется среди уже проверенных отрицательных примеров: высокий `fit(c)` и высокая ошибочная уверенность `preserve(c)` делают пример приоритетным. Нельзя назначать отрицательную метку только формулой `fit - lambda * preserve`.

## 6. Первый эксперимент на H100

Сначала сравниваются три входа на одном checkpoint, одном фиксированном split и одинаковых гиперпараметрах:

- `pair`: полный исходный текст против полного изменённого;
- `marked_pair`: целевая сущность явно размечена в исходном тексте;
- `masked_query`: маскированный контекст плюс исходная сущность и кандидат.

Основные метрики: macro-F1, PR-AUC, ROC-AUC, balanced accuracy и calibration. Обязательно публикуются срезы по `proper/common/numeric`, fine type, domain и candidate kind. Для редких типов показываются интервалы неопределённости или явно указывается малый размер выборки.

Запуск:

```bash
PYTHON_BIN=python \
TRAIN_JSONL=data/semantic_corpus_v1_20260819/train.jsonl \
VAL_JSONL=data/semantic_corpus_v1_20260819/val.jsonl \
TEST_JSONL=data/semantic_corpus_v1_20260819/test.jsonl \
bash mvp/run_semantic_ablation_h100.sh
```

Только после выбора представления имеет смысл менять функцию потерь.

## 7. Ранжирование

В текущем train есть 2 757 `mention_id` с обоими классами и около 12 247 сравнений positive-vs-negative. Такие пары строятся только внутри одного упоминания, поэтому контекст одинаков, а различается кандидат.

```bash
python mvp/prepare_ranking_pairs.py \
  --input data/semantic_corpus_v1_20260819/train.jsonl \
  --out data/semantic_corpus_v1_20260819/ranking_train.jsonl \
  --summary-out data/semantic_corpus_v1_20260819/ranking_summary.json
```

После baseline добавляется `L = L_cls + lambda_rank * L_rank`. Значение `lambda_rank` выбирается по validation, а не по test.

## 8. Двунаправленное следование

Бинарный `changed` нельзя механически преобразовать в entailment/neutral/contradiction: он не сообщает причину изменения. Направленные метки создаются отдельным агентным заданием:

```text
A -> B, B -> A
equivalence | generalization | specialization | substitution | contradiction
```

Для разных собственных имён ожидается чаще `neutral/neutral`, а не contradiction. Структурированная Mistral-разметка запускается отдельно, затем уверенные ответы превращаются в два упорядоченных NLI-примера.

```bash
python mvp/annotate_directional_relations_mistral.py \
  --input data/semantic_corpus_v1_20260819/train.jsonl \
  --out data/directional_relations/train.jsonl \
  --resume

python mvp/prepare_directional_nli_corpus.py \
  --input data/directional_relations/train.jsonl \
  --out data/directional_relations/train_nli.jsonl \
  --summary-out data/directional_relations/train_nli.summary.json
```

Сначала NLI проверяется как отдельная задача и оценивается на вручную просмотренном challenge-наборе. Совместная архитектура `classification + NLI + ranking + MLM` допустима только после успешных отдельных абляций: иначе невозможно понять источник улучшения или деградации.

### 8.1. Общая multi-head модель

`mvp/train_multitask_cross_encoder.py` использует один ModernBERT encoder и
четыре выхода: `preserved/changed`, `A -> B`, `B -> A` и пятичастное отношение.
Ranking loss использует preservation logit. Для строк без направленной метки
NLI/relation losses маскируются, поэтому бинарный корпус не получает выдуманных
`neutral/contradiction` меток.

Офлайн-запуск на уже собранном корпусе:

```bash
PYTHON_BIN=/path/to/python \
DEVICE=cuda PRECISION=bf16 BATCH_SIZE=32 \
bash mvp/run_multitask_cross_encoder_h100.sh
```

Inference после обучения:

```bash
python mvp/score_multitask_pairs.py \
  --checkpoint models/semantic_multitask_.../best \
  --input data/pairs_to_score.jsonl \
  --out data/pairs_to_score.multitask.jsonl \
  --summary-out data/pairs_to_score.multitask.summary.json \
  --device cuda
```

Скорер возвращает preservation probability, `A -> B`, `B -> A`, отношение,
согласованность relation-head с двумя NLI-головами и reject-band `uncertain`.

Направленная разметка накладывается только по точному совпадению `left`, `right`,
`entity`, `candidate`. Служебные `source_pair_id` не используются, поскольку они
повторяются между shard. В текущем фиксированном split точные направленные метки
покрывают 30 train, 3 validation и 5 test строк. Этого достаточно для smoke-
проверки архитектуры, но недостаточно для выбора модели по NLI-F1; пока лучший
checkpoint выбирается по preservation, а directional metrics публикуются как
диагностические.

## 9. Порядок работ

1. Завершить слепой аудит текущего proper-корпуса и зафиксировать отчёт.
2. Прогнать common/numeric smoke-наборы через двух судей и вручную проверить разногласия.
3. Запустить полную генерацию non-proper, не смешивая её с train до консенсуса.
4. Пересобрать фиксированный corpus и отдельные type-balanced challenge-наборы.
5. Выполнить три input-абляции на H100.
6. Добавить ranking loss и динамический hard-negative mining.
7. Отдельно разметить и проверить directional NLI.
8. Только затем тестировать многозадачную модель и MLM-verbalizer как исследовательские абляции.

Главный принцип: генераторы создают кандидатов, агенты создают supervision, а held-out тест никогда не используется для выбора порогов или кандидатов.

## 10. Воспроизводимый запуск и quality gates

### 10.1. Офлайн-запуск на H100

Если на сервере нет интернета, используется отдельный контур
`mvp/run_semantic_offline_h100.sh`. Он не импортирует `.env`, не читает API-
ключи и не запускает Mistral/OpenRouter.

```bash
PYTHON_BIN=/path/to/venv/bin/python \
DEVICE=cuda \
RUN_TRAINING=0 \
bash mvp/run_semantic_offline_h100.sh
```

Он выполняет только локальные операции:

1. аудит уже размеченных имён собственных и старого common-набора;
2. генерация common-кандидатов через ModernBERT, SQLite и WordNet;
3. генерация числовых замен по окну из одного-двух слов слева и справа;
4. расчёт локального MLM-fit на исходном и подставленном контексте;
5. материализация weak/rule labels с признаком `remote_judgment_used=false`;
6. аудит и сборка entity/document-disjoint корпуса;
7. опциональное обучение cross-encoder на H100.

Слабые common-метки явно помечены как `weak_or_rule_based`; это bootstrap-
супервизия, а не золотая разметка. Для подготовки без common-слабых меток:

```bash
INCLUDE_COMMON_WEAK=0 bash mvp/run_semantic_offline_h100.sh
```

Для запуска multi-head обучения после подготовки:

```bash
RUN_TRAINING=1 DEVICE=cuda PRECISION=bf16 BATCH_SIZE=32 \
bash mvp/run_semantic_offline_h100.sh
```

`TRAIN_MODE=multitask` используется по умолчанию. Для контрольного бинарного
запуска задаётся `TRAIN_MODE=binary`. Ranking-пары строятся только из train split
после окончательной entity/document-disjoint разбивки.

Каждый запуск пишет новую папку `data/semantic_pipeline_offline_h100_*` и не
удаляет существующие результаты. Старый `run_semantic_quality_pipeline.sh`
сохраняет сетевой двухсудейный эксперимент как отдельный online-вариант и не
используется в H100 offline-запуске.

Для полного запуска используется `mvp/run_semantic_quality_pipeline.sh`. Он создаёт
новую папку `data/semantic_pipeline_<timestamp>` и не удаляет предыдущие результаты.
Внутри последовательно сохраняются исходные кандидаты, MLM-оценки, ответы обоих
судей, консенсус, итоговый корпус и два аудита качества.

Судьи common и numeric запускаются параллельно: Mistral использует отдельный ключ,
а второй судья по умолчанию идёт через OpenRouter. Для каждой ветки train принимается
только при двух одинаковых ответах (`preserved` или `changed`); `uncertain`, `missing`
и конфликтные ответы остаются в review.

Перед обучением обязательно выполнить dependency-free аудит:

```bash
python mvp/audit_semantic_dataset.py \
  --input corpus=data/semantic_corpus_v1_20260819/all.jsonl \
  --out data/semantic_quality_audit.json \
  --sample-out data/semantic_quality_audit.samples.jsonl
```

В обучающий cross-encoder передаются восстановленные `model_left/model_right`.
Если исходные строки содержат `<mask>`, целевая позиция восстанавливается по
`mask_idx` и проверяется сравнением с candidate-контекстом. Это предотвращает
маркировку другого повторного упоминания той же сущности.
